# HR Warehouse ERP: Setup & Deployment Guide

This guide takes you from "zip file" to "live website" in plain steps.
Think of it like opening a shop:

| Piece | What it is | Shop analogy |
|---|---|---|
| **MongoDB Atlas** | The database (stores all records) | The ledger books in the back room |
| **Cloudinary** | Stores product photos and videos | The photo album |
| **Render** | Runs the backend (the API) | The shopkeeper who follows the rules |
| **Vercel** | Hosts the frontend (the screens) | The shop window and counter |
| **`.env` file** | Secret settings (passwords, keys) | The key to the shop, never shown to anyone |

All four services have free plans that are enough for this project.

---

## Step 0: What you need on your computer

- **Node.js 20 or newer.** Check with `node -v`. Download the LTS version from nodejs.org if needed.
- **Git.** You already have it.

---

## Step 1: Put the code in your repo

1. Unzip `hr-warehouse-erp.zip`.
2. Copy everything inside it into your cloned `hr-warehouse-erp` folder (replace files if asked).
3. Commit and push it on a feature branch, then open a Pull Request into `develop`:

```bash
cd hr-warehouse-erp
git checkout develop
git checkout -b feature/mern-port
git add .
git status            # make sure NO .env file is listed
git commit -m "feat: full MERN port of HR Warehouse ERP"
git push -u origin feature/mern-port
```

---

## Step 2: MongoDB Atlas (database)

1. Sign up at **cloud.mongodb.com**. Create a project called `HR Warehouse`.
2. Click **Create** and choose the **Free (M0)** cluster. Pick the **Mumbai (ap-south-1)** region, since it's closest to Surat.
3. **Database Access** → **Add New Database User**:
   - Username: for example `hrwarehouse`
   - Password: click **Autogenerate** and copy it somewhere safe
   - Role: **Read and write to any database**
4. **Network Access** → **Add IP Address** → **Allow access from anywhere** (`0.0.0.0/0`).
   *Why:* Render's free servers don't have a fixed address. Your database is still protected by the username and password.
5. **Database** → **Connect** → **Drivers**. Copy the connection string. It looks like this:
   ```
   mongodb+srv://hrwarehouse:<db_password>@cluster0.abcde.mongodb.net/?retryWrites=true&w=majority&appName=Cluster0
   ```
6. Replace `<db_password>` with your password, and add the database name `hr-warehouse` after `.net/`:
   ```
   mongodb+srv://hrwarehouse:YOURPASSWORD@cluster0.abcde.mongodb.net/hr-warehouse?retryWrites=true&w=majority&appName=Cluster0
   ```
   That full line is your **`MONGODB_URI`**.

> **Why Atlas even for local work?** The app uses MongoDB *transactions*: a sale changes 5 or 6 records together, and either all of them save or none do (this replaces LockService). Transactions need a "replica set". Atlas always has one. A plain MongoDB installed on your laptop does not, so sales would fail there.
>
> If a password has special characters like `@ : / ?`, Atlas may need them encoded. The easy fix is an autogenerated password with letters and numbers only.

## Step 3: Cloudinary (photos and video)

1. Sign up at **cloudinary.com** (free plan).
2. On the **Dashboard** (or **Settings → API Keys**), copy these three values:
   - **Cloud name** → `CLOUDINARY_CLOUD_NAME`
   - **API Key** → `CLOUDINARY_API_KEY`
   - **API Secret** → `CLOUDINARY_API_SECRET`

Files are stored like the old Google Drive layout:
`HR Warehouse Media / SEL-0001 - Seller Name / Images / Item_Name_001.jpg` and `.../Video/...`.

The app works without Cloudinary. Only the photo and video upload buttons will show "Media storage is not set up".

## Step 4: Create `backend/.env`

Create a file named exactly `.env` inside the `backend` folder. It's already in `.gitignore`, so Git will never upload it.

**4a. Make a JWT secret** (a long random string that signs the login "pass"):

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

**4b. Make the admin password hash.** The password itself is never stored, only a scrambled version of it:

```bash
cd backend
npm install
npm run hash-password -- "Choose-A-Strong-Password"
```

It prints a line starting with `ADMIN_PASSWORD_HASH=$2b$12$...`. Copy that whole line.

**4c. Fill in `backend/.env`:**

```
PORT=5000
NODE_ENV=development
MONGODB_URI=mongodb+srv://hrwarehouse:YOURPASSWORD@cluster0.abcde.mongodb.net/hr-warehouse?retryWrites=true&w=majority&appName=Cluster0
JWT_SECRET=paste-the-long-random-string-from-4a
ADMIN_USERNAME=admin
ADMIN_PASSWORD_HASH=paste-the-hash-from-4b
FRONTEND_URL=http://localhost:5173
CLOUDINARY_CLOUD_NAME=your-cloud-name
CLOUDINARY_API_KEY=your-api-key
CLOUDINARY_API_SECRET=your-api-secret
```

**`frontend/.env` is optional now.** The app calls `/api` by default. In development, Vite forwards those calls to `localhost:5000` (see `frontend/vite.config.js`). In production, Vercel forwards them to Render (Step 7). If you do keep a `frontend/.env`, either leave it empty or use `VITE_API_URL=http://localhost:5000/api`. Both work locally.

## Step 5: Run it on your computer

Open two terminals.

```bash
# Terminal 1: backend
cd backend
npm install
npm run dev
# You should see: "MongoDB connected" and "API running on port 5000"
```

```bash
# Terminal 2: frontend
cd frontend
npm install
npm run dev
# Open http://localhost:5173
```

Log in with `admin` and the password you chose in 4b.
On first start, the backend adds the default Settings (capacity 4000 sq.ft, rate ₹25, commission 10%...) and the 4 default categories by itself.

**Quick test, in this order:** add a seller → add a buyer → Add Product → Sell / Billing → Sales / Orders (Collect, then Deliver) → Settlements → Storage Billing → System Management → Run health check.

**Automatic test (optional):** `cd backend && npm test`. It runs the whole sale flow on a throwaway database. The first run downloads a test copy of MongoDB, so it takes a minute.

## Step 6 (only if the client has real data): Import the old Google Sheet

1. In the old Google Sheet, download each tab with **File → Download → Comma-separated values (.csv)**.
2. Rename the files to match the tab names exactly and put them in one folder, for example `backend/sheet-export/`:
   `Sellers.csv, Buyers.csv, Assets.csv, Sales.csv, Payments.csv, Settlements.csv, StorageLedger.csv, InventoryLedger.csv, Categories.csv, CustomFields.csv, Expenses.csv, Settings.csv, AuditLog.csv, Reversals.csv`
3. Run the import:
   ```bash
   cd backend
   npm run import:sheet -- ./sheet-export
   ```
4. Open the app → **System Management → Run health check**. It should say "All good".
5. Delete the `sheet-export` folder afterwards. It holds business data and must not go into Git.

New IDs continue from the imported ones. If the last seller was SEL-0042, the next one is SEL-0043.

## Step 7: Go live (Render + Vercel)

Do this from the `main` branch: merge `feature → develop → main` with Pull Requests first.

### 7a. Backend on Render

1. Sign up at **render.com** with your GitHub account. Allow access to the `hr-warehouse-erp` repo.
2. **New → Web Service** → choose the repo.
3. Settings:

| Setting | Value |
|---|---|
| Name | `hr-warehouse-api` (this becomes `https://hr-warehouse-api.onrender.com`) |
| Region | Singapore (closest to India) |
| Branch | `main` |
| Root Directory | `backend` |
| Runtime | Node |
| Build Command | `npm install` |
| Start Command | `npm start` |
| Instance type | Free |
| Health Check Path (under Advanced) | `/api/ping` |

4. **Environment Variables:** add each of these. Use the same values as your `.env`, except the ones marked:

| Key | Value |
|---|---|
| `NODE_ENV` | `production` ← different |
| `MONGODB_URI` | same as `.env` |
| `JWT_SECRET` | make a **new** one for production (Step 4a) |
| `ADMIN_USERNAME` | same |
| `ADMIN_PASSWORD_HASH` | same, or a new hash for a different live password |
| `FRONTEND_URL` | your Vercel address from 7b, e.g. `https://hr-warehouse-erp.vercel.app` (fill in after 7b) |
| `CLOUDINARY_CLOUD_NAME` | same |
| `CLOUDINARY_API_KEY` | same |
| `CLOUDINARY_API_SECRET` | same |

   You don't need to add `PORT`. Render sets it by itself.

5. Click **Create Web Service**. When the log shows "API running", open `https://hr-warehouse-api.onrender.com/api/ping`. It should show `{"success":true,"data":"ok"}`.

> **Free plan note:** Render's free servers go to sleep after about 15 minutes with no visits. The next visit takes 30–60 seconds to wake it up. Render's cheapest paid plan avoids this if the client finds it annoying.

### 7b. Frontend on Vercel

1. Open `frontend/vercel.json` and replace `YOUR-BACKEND-NAME` with your Render name:
   ```json
   { "source": "/api/:path*", "destination": "https://hr-warehouse-api.onrender.com/api/:path*" }
   ```
   Commit and push this change (it has to reach `main`).
2. Sign up at **vercel.com** with GitHub → **Add New → Project** → import `hr-warehouse-erp`.
3. Settings:

| Setting | Value |
|---|---|
| Root Directory | `frontend` |
| Framework Preset | Vite (detected automatically) |
| Build Command | `npm run build` |
| Output Directory | `dist` |
| Environment Variables | **none needed** |
| Production Branch (Settings → Git) | `main` |

4. Click **Deploy**. You get an address like `https://hr-warehouse-erp.vercel.app`.
5. Go back to Render → Environment → set `FRONTEND_URL` to that address (no slash at the end) → Save. Render restarts by itself.
6. Open the Vercel address and log in. 🎉

> **Why the `vercel.json` forwarding?** The login is kept in a secure cookie. If the website (vercel.app) and the API (onrender.com) talk to each other directly, some browsers, especially Safari on iPhone, block that cookie as "third-party". With the forwarding, the browser only ever talks to vercel.app, so the cookie always works.

### 7c. After that: deploying changes (CD)

- Open a Pull Request (`feature/... → develop`). **GitHub Actions CI** (`.github/workflows/ci.yml`) runs tests, lint and build automatically.
- Merge `develop → main`. **Render and Vercel deploy automatically** from `main`. Nothing else to do.
- Optional: in Vercel, preview deployments for `develop` give you a test link before going live.

## All settings in one place

| Name | Where it goes | What it is |
|---|---|---|
| `PORT` | backend `.env` only | `5000` locally. Render sets its own. |
| `NODE_ENV` | `.env` = `development`, Render = `production` | Turns on HTTPS-only cookies in production |
| `MONGODB_URI` | `.env` + Render | Atlas connection string with `/hr-warehouse` |
| `JWT_SECRET` | `.env` + Render (different values) | Long random string that signs logins |
| `ADMIN_USERNAME` | `.env` + Render | Login name |
| `ADMIN_PASSWORD_HASH` | `.env` + Render | From `npm run hash-password` |
| `FRONTEND_URL` | `.env` = `http://localhost:5173`, Render = Vercel URL | Which website may call the API. Separate several with commas. |
| `CLOUDINARY_CLOUD_NAME` / `_API_KEY` / `_API_SECRET` | `.env` + Render | Photo/video storage |
| `VITE_API_URL` | optional, frontend | Leave unset. The default `/api` works locally and on Vercel. |
| Render URL | `frontend/vercel.json` | Where Vercel forwards `/api` calls |

GitHub Secrets are **not needed**: CI uses a throwaway test database, and Render/Vercel keep their own settings.

## Everyday admin tasks

- **Change the login password:** run `npm run hash-password -- "NewPassword"`, put the new hash in Render → Environment → `ADMIN_PASSWORD_HASH`, and save. There is no "forgot password" screen, by design.
- **Log everyone out (e.g. a laptop was lost):** change `JWT_SECRET` on Render. Every existing login stops working.
- **If a `.env` is ever committed by mistake:** deleting the file isn't enough, because Git keeps history. Change every secret inside it: Atlas user password, `JWT_SECRET`, admin password, and Cloudinary secret (Cloudinary → Settings → API Keys → regenerate).
- **Backups:** the Atlas free tier has no automatic backups. Once a month, export the data with MongoDB Compass (free app → connect with `MONGODB_URI` → each collection → Export).

## Troubleshooting

| You see | Likely cause → fix |
|---|---|
| `Missing environment variables: ...` | `.env` is not in the `backend` folder, or a line is misspelled |
| `ADMIN_PASSWORD_HASH must be a bcrypt hash` | You pasted the password instead of the hash. Run Step 4b. |
| `querySrv ENOTFOUND` / `bad auth` on start | Wrong `MONGODB_URI` or password. Re-copy from Atlas. |
| Backend hangs at start, then times out | Atlas Network Access doesn't allow your IP. Use `0.0.0.0/0`. |
| "Transaction numbers are only allowed on a replica set" | You're using a local MongoDB. Use Atlas. |
| Login works locally but not on the live site | `FRONTEND_URL` on Render doesn't exactly match the Vercel URL, or `vercel.json` still says `YOUR-BACKEND-NAME` |
| `Origin not allowed` | Same as above: fix `FRONTEND_URL` (no slash at the end) |
| "Too many failed login attempts" | 5 wrong passwords in 15 minutes. Wait 15 minutes. |
| "Media storage is not set up" | The Cloudinary values are missing on Render or in `.env` |
| First page load takes ~1 minute | Render free server waking up (see 7a) |

## Things to confirm against the old system

The port follows the handoff notes exactly. A few small details were not covered by the notes, so I picked the most likely behaviour. If you re-share `flow_code.txt` and `html.txt`, these can be checked line by line:

1. **Edit seller / edit buyer** buttons exist (name, phone, email, address, GSTIN, KYC).
2. **KYC status** choices are Pending / Verified / Rejected.
3. **Payment modes** are Cash / UPI / Bank Transfer / Card / Cheque.
4. **Archiving a seller** is blocked if *any* product was ever linked to them (including sold or archived ones).
5. **Adjust quantity** is not allowed on Sold or Archived products.
6. **Storage billing** skips a product when its new charge rounds to ₹0. Those days are billed on the next run, so nothing is lost.
7. **Dead stock** lists only products that still have available units.
8. **Dashboard "Items in stock"** = total available units (not counting reserved).

Known quirks of the old system were **kept on purpose** (seller credited at reservation, rent can make payable negative, flat commission, "Listed" is just a label, `StorageCharge` always 0, billing accrues up to "now").
